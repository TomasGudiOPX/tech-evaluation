## Problem Statement

Build a compact, good-looking shopping-cart application for the technical evaluation. It must demonstrate a complete customer workflow—catalog, cart, authentication, simulated checkout, and order history—plus a focused administrator workflow for product management. The learning objective is to understand how a small full-stack modular monolith is designed, tested, documented, and critically developed with AI tools.

## What Makes This Cool

The app is a deliberately small Amazon-style store, but the evaluator can inspect how it was made. An Obsidian-compatible vault and OpenSpec records provide an evidence trail from evaluation requirement to design decision, prompt/tool use, AI output, human review or rejection, test, implementation, and commit. The polished UI makes the product easy to demo; the traceability makes the engineering judgment credible.

## Constraints

- Target: Training / Junior / Junior-Advanced evaluation; estimated delivery window: 3–5 days.
- Use TypeScript with Next.js for the web app, NestJS for the API, PostgreSQL, and an ORM with versioned migrations.
- Keep a modular monolith: one deployable API organized by domain modules, one web app, one PostgreSQL database, and no microservices, queues, or real payment provider.
- Include customer and administrator roles; restrict administration to focused product CRUD.
- Maintain documentation as work happens, not retroactively: Obsidian vault, OpenSpec, README, and INFORME_IA.md.
- Preserve existing production principles where practical: Docker Compose, single public entry point, environment-based secrets, and internal API/database services.
- Use Prisma for PostgreSQL access and versioned migrations.
- Use Next.js standalone output in its own internal Compose service behind Nginx; Nginx remains the only public entry point.
- The tracked Obsidian vault lives at `docs/obsidian-vault/`; it contains an index, requirements map, decision records, AI interaction/review notes, and evidence links.
- Commit a complete `.env.example` covering database, JWT, and development-admin seed variables, with no secrets committed.

## Premises

1. This is not an Amazon clone; the goal is a compact, polished commerce workflow that demonstrates junior-to-junior-advanced engineering skill.
2. The core slice includes customer and administrator authentication/authorization, but excludes real payments, marketplace behavior, and undefined 10x scope.
3. Obsidian and OpenSpec traceability must be contemporaneous, linking requirements, decisions, prompts, AI corrections, tests, and commits.

## Approaches Considered

### Approach A: Evolve the existing Fastify/Vite template

Keep React/Vite + Fastify + PostgreSQL and replace the sample projects feature with auth, products, cart, and orders modules.

- Effort: M; Risk: Low
- Pros: Reuses the working template; fastest implementation route; preserves existing deployment shape.
- Cons: Does not use the suggested Next.js/NestJS stack; may show less intentional framework learning.

### Approach B: Next.js + NestJS modular monolith with traceability discipline (chosen)

Rebuild the application using Next.js for the customer/admin UI, NestJS domain modules for the API, PostgreSQL, and an ORM with migrations. Apply a documentation-first, test-driven traceability loop to each vertical slice.

- Effort: L; Risk: Medium
- Pros: Matches the suggested evaluation stack; makes modular-monolith structure explicit; supports strong validation, API documentation, role guards, and tests; creates compelling evidence of deliberate tool use and review.
- Cons: Replaces a working template; requires strict scope control to protect time for UI polish and documentation.

### Approach C: Documentation-first slices on the existing stack

Keep the current stack but make every feature a repeatable cycle: OpenSpec, failing test, implementation, Obsidian note, review/correction, and commit.

- Effort: M; Risk: Medium
- Pros: Strongest immediate evidence of TDD and traceability; minimal platform work.
- Cons: Less framework breadth; process overhead can delay UI polish.

## Recommended Approach

Use Approach B with Approach C's discipline. The modular NestJS API will own auth, products, cart, and orders as cohesive domain modules; the Next.js app will provide customer and administrator experiences. Every slice receives a lightweight requirement-to-commit evidence link, while the identity and checkout slices receive complete OpenSpec → test → implementation → AI review/correction → Obsidian evidence → commit chains. This preserves the evaluation's differentiated AI-use criteria without making the process heavier than the 3–5 day delivery window.

## Architecture and Delivery Contracts

- **Modules and data ownership:** `auth` owns `User` and role identity; `products` owns `Product`; `cart` owns authenticated `Cart` and `CartItem`; `orders` owns `Order` and immutable `OrderItem` price/quantity snapshots. Controllers do not cross module repositories directly.
- **Cart policy:** browsing is public; adding or changing a cart requires login and persists in the authenticated user's database cart. This is simpler and more auditable than a guest-cart merge flow; the README documents the choice.
- **RBAC policy:** public registration always creates a `customer`; no request can select its own role. A development seed creates the first `admin` from environment-controlled credentials. Administrator product retirement is a soft deactivation: retired products are excluded from the catalog and cannot be checked out.
- **Checkout invariant:** a database transaction locks requested active products in ascending product-ID order, verifies available stock, decrements stock, creates the order and immutable price snapshots, then clears the cart. If any line is unavailable, the transaction creates no order and returns a structured `409` insufficient-stock response. A required integration test runs two simultaneous checkouts for the final unit: exactly one succeeds and the other receives `409`.
- **Idempotency:** `POST /orders/checkout` requires an `Idempotency-Key` header. Keys are unique per `(userId, key)`, retain the request fingerprint and result for 24 hours, and return the original order for an identical retry. Reusing a key with a different request returns structured `409` `IDEMPOTENCY_KEY_REUSED`.
- **API outline:** public `GET /products` and `GET /products/:id`; auth registration/login/profile endpoints; authenticated `GET /cart`, `POST /cart/items`, `PATCH /cart/items/:productId`, and `DELETE /cart/items/:productId`; authenticated `POST /orders/checkout` and `GET /orders`; administrator create/read/update/retire product endpoints. “CRUD” intentionally excludes hard delete; retirement is the only product removal behavior. NestJS Swagger publishes the REST contract.
- **Error envelope:** all expected failures return `{ code, message, fieldErrors? }`; validation uses `fieldErrors`, authentication/authorization uses stable codes, and domain conflicts use `409` with a stable code. No stack traces are exposed.
- **Testing:** required: auth and product service tests, checkout integration tests for success/insufficient stock/idempotency/concurrent final-unit checkout, RBAC route tests, and one end-to-end customer happy path. Checkout is TDD-first; other modules retain documented tests and may add tests immediately after implementation where test-first would not add learning value.
- **Evidence schema:** every tracked requirement uses an ID, with a vault entry containing `Requirement ID → OpenSpec change/spec → decision → representative prompt/tool output → human acceptance/rejection → test → implementation paths → commit`. At least the identity and checkout slices must have complete chains.

## Scope and Timebox

| Priority | Commitment |
| --- | --- |
| Must | Next.js/NestJS/Prisma setup; responsive catalog/detail with a small deterministic seed catalog; authenticated cart; registration/login/JWT/RBAC; atomic simulated checkout; order history; seeded admin; admin product CRUD; migrations; Swagger; defined tests; Obsidian/OpenSpec/INFORME_IA evidence; complete `.env.example`; Docker Compose; GitHub Actions CI. |
| Should | Enhanced visual polish, validation/error polish beyond the defined envelope, and one complete evaluator walkthrough. |
| Defer | Search/filter, pagination, SSR/ISR justification beyond the selected Next runtime, rate limiting, guest-cart merge, real payments, public deployment, and marketplace features. |

**Day-1 delivery gate:** if the Next.js/NestJS workspace, PostgreSQL migration, Compose startup, and login baseline do not work by the end of day 1, defer every `Should` item and protect the Must scope, tests, and traceability. Do not recover time by removing verification or documentation.

**Cut lines:** by end of day 2, protect catalog, identity, and the authenticated cart; by end of day 3, protect atomic checkout and order history; by end of day 4, protect the admin panel, automated test set, and evidence chain. If a cut line is missed, defer CI refinements and enhanced visual polish before deferring checkout, tests, or traceability.

## Success Criteria

- A visitor can browse a responsive catalog and product details; an authenticated user can manage their persistent cart.
- A user can register, log in, check out a simulated order, and view only their own order history.
- An administrator can authenticate and create, edit, or soft-retire products through a restricted panel; self-registration never grants administration.
- API input validation, structured error responses, JWT authentication, role authorization, and the defined atomic checkout invariant are implemented and documented.
- The API has generated Swagger REST documentation; Prisma migrations, automated tests, lint/formatting, Docker Compose, and GitHub Actions CI run reproducibly.
- The repository contains an Obsidian-compatible vault, OpenSpec changes/specifications, README decisions, and INFORME_IA.md linking representative prompts, tool/agent usage, rejected/corrected outputs, TDD examples, and the final reflection.
- The evaluator can follow at least one complete evidence chain from evaluation requirement to spec, test, implementation, correction, and descriptive commit.

## Distribution Plan

The project is delivered as a Git repository and can be run locally with Docker Compose. CI runs linting, tests, and builds on pull requests. A public deployment is optional and is not required for the evaluation; if added, it follows the existing single-VPS/single-public-entry-point design.
